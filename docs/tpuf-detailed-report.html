turbopuffer vs Qdrant Cloud
Detailed Benchmark Report

Three datasets, four concurrency levels, upload throughput, filtered search, multi-tenant isolation, and cost modeling — from a single EC2 host in aws-us-west-2, same region as both services.

● turbopuffer ● Qdrant Cloud aws-us-west-2 100K–105K vectors 768–2048 dims
TL;DR — who wins, when

No universal winner: the choice is a function of your query load, filter selectivity, and tenancy. Both engines reach ~80 RPS from a single client here; the real differences are recall, latency floor, write scaling, and cost shape.

● Choose turbopuffer when

  • Traffic is bursty, low-QPS, or idle-heavy — usage pricing (+$16/mo floor) beats an always-on node below ~9 QPS (DBpedia/H&M) or ~25 QPS (multi-tenant).
  • You run many mostly-idle tenants — serverless scales to zero.
  • Write/ingest throughput matters — tpuf scales 430→1237 WPS vs Qdrant’s flat ~90.
  • Unfiltered or multi-tenant recall (near-parity) is sufficient.

● Choose Qdrant Cloud when

  • Filtered-search recall is critical — 95.85% vs tpuf’s structural, un-tunable 89.14%.
  • You need a low, predictable latency floor — ~2ms server, no cold-start (tpuf floors ~10ms and can cold-start to ~1.9s).
  • Load is steady and above the break-even — a fixed node is cheaper per query at scale.
  • You want recall tunability (ef, quantization) or dedicated isolation.
Cost crossover: tpuf is cheaper below ~9 QPS (DBpedia/H&M) / ~25 QPS (multi-tenant); above that Qdrant’s flat node wins (full model in §4.2). Three cost lenses: tpuf usage · Qdrant managed · raw hardware.
§1

What is turbopuffer?

turbopuffer is an S3-backed vector database built around SPFresh centroid-based ANN search. It stores the vector index on object storage and uses a local NVMe cache to accelerate repeated queries. It offers two deployment modes — serverless and pinned — and deliberately exposes no recall tuning knobs.

  • No recall tuning. Locked at 89.14% recall on filtered search and 98.51% on unfiltered. You cannot trade latency for recall.
  • Serverless mode. Shared compute, scales to zero between queries, inherent noisy-neighbor risk when multiple namespaces share a host.
  • Pinned mode. Dedicated NVMe, fixed replicas, full machine isolation. Eliminates noisy-neighbor contention but removes scale-to-zero savings.
  • Cold-start penalty. After any restart, the first queries must fetch index data from S3 before NVMe is warm. Penalty: 100–1500ms on first queries, converging to steady-state after ~30 requests.
  • SPFresh algorithm. Centroid-based ANN that post-filters for attribute predicates rather than integrating filters into graph traversal. Leads to measurable recall drops under selective filter conditions.
  • Write pipeline & index visibility. Writes are group-committed (100–250ms window) and flushed as an append-only WAL entry to S3. Indexing (SPFresh centroid tree) is asynchronous — new vectors are immediately readable via exhaustive WAL scan before the index is built. There is no write-blocking indexing phase (unlike Qdrant’s HNSW build). With strong consistency (default), each query checks S3 for the latest WAL version, adding ~10ms overhead — this is the architectural source of the 10ms server-side latency floor. Eventual consistency mode skips this check (sub-10ms possible, up to ~1h staleness).

Filtered vector search is where architecture choices have the sharpest consequences. SPFresh (turbopuffer) post-filters: it traverses centroids first, then discards non-matching vectors. SPFresh post-filters after centroid traversal — vectors matching the filter may not be in the traversed centroid regions at all. Qdrant's filter-aware HNSW traversal constrains the graph walk to matching nodes, preserving recall. The ~7% gap (89.14% vs 95.85%) is not tunable on turbopuffer.

Pinned Mode: Billing Economics

Pinned mode keeps a turbopuffer namespace resident on dedicated hardware, eliminating serverless cold-start variance for any query type. The tradeoff is economic: pinned billing applies a 64 GB floor regardless of actual data size, making it prohibitively expensive for small datasets.

9.1 — Billing Model

Pinned namespace billing is documented at turbopuffer.com/docs/pinning. Two key facts are stated explicitly:

  • 64 GB minimum: “namespaces smaller than 64 GB are billed at 64 GB”
  • Rate example: a 256 GB namespace at 1 replica = $2,476/month (storage component)

From these two facts the per-GB-hr rate is derived:

rate  = $2,476 ÷ (256 GB × 730 hr/mo)  =  $0.01325 / GB-hr

monthly cost  =  max(actual_gb, 64) × replicas × 730 × $0.01325
             +  actual_gb × $0.33   (storage, billed separately)

floor check:  64 GB × 1r × 730 × $0.01325  =  $619 / replica / mo
              64 GB × 4r × 730 × $0.01325  =  $2,476 / mo  ← matches published 4r example

For the H&M benchmark dataset (0.43 GB actual), pinned 4-replica costs $2,476/month — 79× more than Qdrant's $31.18 — while delivering worse single-stream performance (47.4 vs 149.6 RPS at p=1 — a latency comparison, not capacity), worse p99 (50ms hot vs 9.9ms), and lower recall (89.14% vs 95.85%). For datasets under ~5 GB, pinning is strictly worse on every dimension: cost, latency, and recall.

9.2 — Break-Even Analysis

Pinned mode bills the 64 GB floor: even the 0.3–0.9 GB benchmark datasets cost 64 GB × 730 hr × $0.01325 = $619/mo at 1 replica ($2,476 at 4). Qdrant serves the same datasets for $31–$82/mo — so pinned turbopuffer has no cost break-even below 64 GB of actual data: it is ~8–20× Qdrant at 1 replica and ~30–80× at 4, at any QPS. Pinning only starts to pay off above ~64 GB (where billing tracks real data), and even then it’s a bet on dedicated NVMe + zero cold-start, not on price.

The serverless cost crossover (~9–25 QPS) applies only to serverless mode. When filtered search or isolation requirements force pinning, that crossover disappears entirely: pinned 1r is $619/mo minimum (64 GB floor) and 4r is $2,476/mo — both far above Qdrant’s $31–$82 for these datasets, at any QPS.

Strategic Implications

These results point to specific architectural decisions rather than a simple winner. The right choice is a function of your QPS profile, filter selectivity, tenant concurrency pattern, dataset size, and tolerance for cold-start latency.

  1. Below its break-even QPS, serverless turbopuffer saves money. That break-even is ~9 QPS for DBpedia & H&M (Qdrant fits a $31 2 GB node) but ~25 QPS for multi-tenant (Qdrant needs an $82 8 GB node) — the bigger the Qdrant node your data forces, the higher the break-even. Above it, Qdrant is cheaper and faster. This only applies to serverless mode.
  2. Pinned mode has a billing floor that dominates small datasets. For any dataset under ~10 GB, pinned turbopuffer costs 10–79× more than Qdrant Cloud with no performance benefit. Workloads that need consistent low-latency (no cold-start variance) pay this premium regardless of query type.
  3. Serverless noisy-neighbor is a real operational risk. A single bursty tenant in serverless mode triples all other tenants' p50 latency. Pinning eliminates this but removes scale-to-zero. Design your tenancy model before choosing serverless.
  4. Filtered search recall is not tunable on turbopuffer. If your workload uses selective attribute filters and 89.14% recall is insufficient, Qdrant is the only option. This constraint is architectural, not a configuration gap.
  5. Multi-tenant idle SaaS is turbopuffer's strongest case. If most tenants are mostly idle, scale-to-zero is worth real money. At active-tenant load Qdrant leads single-stream (57 vs 24 RPS measured at p=1), but under heavy concurrency (p=32) tpuf holds ~94 RPS while the 2-CPU Qdrant node saturates to ~57 RPS. Size the Qdrant node to the concurrency you expect.
  6. Cold-start latency must be part of your SLA calculation. The 1,891ms p99 cold-start is not a fringe edge case — it occurs after any restart, any scale-to-zero event in serverless mode. Plan pre-warm queries or accept the SLA window.

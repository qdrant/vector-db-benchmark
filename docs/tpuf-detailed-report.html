Detailed Benchmark Report

Three datasets, four concurrency levels, upload throughput, filtered search, multi-tenant isolation, and cost modeling — from a single EC2 host in aws-us-west-2, same region as both services.

● turbopuffer ● Qdrant Cloud aws-us-west-2 100K–105K vectors 768–2048 dims
§1

What is turbopuffer?

turbopuffer is an S3-backed vector database built around SPFresh centroid-based ANN search. It stores the vector index on object storage and uses a local NVMe cache to accelerate repeated queries. It offers two deployment modes — serverless and pinned — and deliberately exposes no recall tuning knobs.

  • No recall tuning. Locked at 89.14% recall on filtered search and 98.51% on unfiltered. You cannot trade latency for recall.
  • Serverless mode. Shared compute, scales to zero between queries, inherent noisy-neighbor risk when multiple namespaces share a host.
  • Pinned mode. Dedicated NVMe, fixed replicas, full machine isolation. Eliminates noisy-neighbor contention but removes scale-to-zero savings.
  • Cold-start penalty. After any restart, the first queries must fetch index data from S3 before NVMe is warm. Penalty: 100–1500ms on first queries, converging to steady-state after ~30 requests.
  • SPFresh algorithm. Centroid-based ANN that post-filters for attribute predicates rather than integrating filters into graph traversal. Leads to measurable recall drops under selective filter conditions.
  • Write pipeline & index visibility. Writes are group-committed (100–250ms window) and flushed as an append-only WAL entry to S3. Indexing (SPFresh centroid tree) is asynchronous — new vectors are immediately readable via exhaustive WAL scan before the index is built. There is no write-blocking indexing phase (unlike Qdrant’s HNSW build). With strong consistency (default), each query checks S3 for the latest WAL version, adding ~10ms overhead — this is the architectural source of the 10ms server-side latency floor. Eventual consistency mode skips this check (sub-10ms possible, up to ~1h staleness).

Multi-tenant upload: parallel (tpuf) vs sequential (Qdrant) — methodology drives most of the 8.5× gap
The multi-tenant dataset is 1M vectors total (100 tenants × 10K each) — 10× more data than DBpedia. Qdrant uploads all 1M sequentially in batches to one collection (payload_m=16, is_tenant=True), building per-tenant HNSW sub-graphs in the background. turbopuffer uploads 100 namespaces in parallel (asyncio.gather, semaphore=10 concurrent), so its 2.4 min wall-clock reflects parallel throughput. Sequential uploads at ~624 WPS per namespace would take ~26.7 min (100 × ~16s) — parallelism delivers an ~11× speedup. Both engines use the same batch size (128 vectors/batch). The methodology difference (parallel vs sequential) accounts for most of the 8.5× wall-clock gap; Qdrant also pays extra for HNSW sub-graph construction at write time.
Write-time vs query-time — Qdrant builds HNSW upfront; tpuf defers indexing to async SPFresh
turbopuffer stores 0.615 GB for DBpedia (≈ raw vector size: 100K × 1536-dim × 4B). Qdrant builds HNSW at write time — 168s for H&M, ~0s for DBpedia (index during upload), 5.1s for MT sub-graphs. This one-time write cost is the source of Qdrant’s 1.9ms internal search latency: the index is in RAM, already built. turbopuffer’s SPFresh index is built asynchronously after writes commit to the S3 WAL — writes return immediately (no blocking index phase). SPFresh duration depends on shared indexer availability and varied from 25s to 268s across 5 DBpedia runs. During the SPFresh window, WAL vectors are brute-force scanned per query. Once built, queries use the centroid index from NVMe.
tpuf writes 50–60% faster, but SPFresh build time (25–268s) decides the DBpedia race
, but SPFresh builds the centroid index asynchronously on shared background indexers, and its duration depends on indexer availability at the time of upload. Across 5 DBpedia re-runs, SPFresh completed in 25s, 36s, 61s, 183s, and 268s — putting tpuf total at 3.1–7.3 min. Qdrant’s consistent 3.9 min falls inside that range: tpuf wins when indexers are available, Qdrant wins when they are not. H&M measured 60s SPFresh (4.1 min total) and beat Qdrant (8.4 min) — though with only one H&M trial, the SPFresh variance seen on DBpedia (25–268s) means the margin could narrow to ~0.8 min on a slow indexer draw. Building the index after upload (5.3 min DBpedia, 9.1 min H&M) is slower than building it during upload (3.9 min, 8.4 min) — so Qdrant's default index-during-upload is optimal here, and the bulk-load recipe (disable indexing, then reindex) does not help at this scale.

Pinned Mode: Billing Economics

Pinned mode keeps a turbopuffer namespace resident on dedicated hardware, eliminating serverless cold-start variance for any query type. The tradeoff is economic: pinned billing applies a 64 GB floor regardless of actual data size, making it prohibitively expensive for small datasets.

9.1 — Billing Model

Pinned namespace billing is documented at turbopuffer.com/docs/pinning. Two key facts are stated explicitly:

  • 64 GB minimum: “namespaces smaller than 64 GB are billed at 64 GB”
  • Rate example: a 256 GB namespace at 1 replica = $2,476/month (storage component)

From these two facts the per-GB-hr rate is derived:

rate  = $2,476 ÷ (256 GB × 730 hr/mo)  =  $0.01325 / GB-hr

monthly cost  =  max(actual_gb, 64) × replicas × 730 × $0.01325
             +  actual_gb × $0.33   (storage, billed separately)

floor check:  64 GB × 1r × 730 × $0.01325  =  $619 / replica / mo
              64 GB × 4r × 730 × $0.01325  =  $2,476 / mo  ← matches published 4r example

For the H&M benchmark dataset (0.43 GB actual), pinned 4-replica costs $2,476/month — 95× more than Qdrant's $26.10 — while delivering worse single-stream performance (47.4 vs 149.6 RPS at p=1 — a latency comparison, not capacity), worse p99 (50ms hot vs 9.9ms), and lower recall (89.14% vs 95.85%). For datasets under ~5 GB, pinning is strictly worse on every dimension: cost, latency, and recall.

9.2 — Break-Even Analysis

For pinned 1-replica to match Qdrant's $26.10/month node cost, actual data must exceed 2.7 GB (so billing escapes the 64 GB floor and the compute cost drops below $26.10). That is approximately:

  • ~900K vectors at 1536-dim
  • ~1.8M vectors at 768-dim
  • ~350K vectors at 2048-dim (e.g. OpenAI text-embedding-3-large)

Below these sizes, Qdrant is cheaper even at zero QPS. At 4 replicas (required for reliable filtered search in production), there is no break-even at all — 4 replicas is the same data replicated, not 4× more data capacity. The minimum 4r cost ($2,476) always exceeds Qdrant's $26.10 regardless of dataset size.

The "~8–13 QPS cost crossover" applies only to serverless mode. When filtered search or isolation requirements force pinning, that crossover disappears entirely. For pinned 1r, break-even requires >2.7 GB actual data. For pinned 4r, there is no break-even — $2,476/month minimum vs $26.10.

Strategic Implications

These results point to specific architectural decisions rather than a simple winner. The right choice is a function of your QPS profile, filter selectivity, tenant concurrency pattern, dataset size, and tolerance for cold-start latency.

  1. Below ~8–13 QPS/namespace (scale-dependent), serverless turbopuffer saves money. Above it, Qdrant is both cheaper and faster. The break-even is stable across dataset scales — plan around it. This only applies to serverless mode.
  2. Pinned mode has a billing floor that dominates small datasets. For any dataset under ~10 GB, pinned turbopuffer costs 10–95× more than Qdrant Cloud with no performance benefit. Workloads that need consistent low-latency (no cold-start variance) pay this premium regardless of query type.
  3. Serverless noisy-neighbor is a real operational risk. A single bursty tenant in serverless mode triples all other tenants' p50 latency. Pinning eliminates this but removes scale-to-zero. Design your tenancy model before choosing serverless.
  4. Filtered search recall is not tunable on turbopuffer. If your workload uses selective attribute filters and 89.14% recall is insufficient, Qdrant is the only option. This constraint is architectural, not a configuration gap.
  5. Multi-tenant idle SaaS is turbopuffer's strongest case. If most tenants are mostly idle, scale-to-zero is worth real money. At active-tenant load, Qdrant is 5.5× faster per request (184.6 vs 33.5 RPS single-stream) — though under heavy concurrency (p=32) tpuf’s autoscaling out-delivers the saturated 2CPU Qdrant node in total throughput (~538 vs ~304 RPS). Size the Qdrant node to the concurrency you expect.
  6. Cold-start latency must be part of your SLA calculation. The 1,891ms p99 cold-start is not a fringe edge case — it occurs after any restart, any scale-to-zero event in serverless mode. Plan pre-warm queries or accept the SLA window.

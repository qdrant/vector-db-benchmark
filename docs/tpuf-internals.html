turbopuffer Internals & Deep Dives

Nine operational deep-dives into how turbopuffer behaves under the hood — cold-start, replica boot, scaling, contention, concurrent writes — and how Qdrant disk mode compares.

← Main benchmark report

Nine experiments that reveal how turbopuffer behaves under the hood and how it compares to Qdrant disk mode. Key findings: (1) SPFresh does lazy per-centroid NVMe caching — ~75 sequential queries to reach stable warm latency, no global pre-fetch. (2) A single pinned replica saturates at ~6–8 CPU cores; serverless outperforms it at p≥8. (3) Correctly-warmed 4-replica pinned peaks at 473 RPS — NVMe bandwidth, not CPU, is the ceiling. (4) A pinned replica takes ~80s to become ready and is still cold after that — first query hits ~600ms. (5) hint_cache_warm used inline is 13× worse than default — it is for pre-warming, not per-query prefix. (6) All namespaces under one API key share one physical machine in serverless mode; a bursty tenant degrades all others ~3×. (7) Pinning has zero effect on write throughput (624 vs 633 WPS). (8) During concurrent writes, tpuf's WAL exhaustive scan rescues recall at the cost of 1.8× higher p99 — latency normalises within seconds of indexing completing. (9) Qdrant disk mode has bimodal behavior: p99=1,457ms cold (EBS random I/O storm) vs p99=10ms warm — once 586 MB fits in OS page cache the disk-mode penalty disappears entirely.

Replica Boot Time

How long does it take to go from "pin namespace" to "serving warm traffic"? We called update_metadata(pinning={"replicas": 1}) and polled ns.metadata() every 5 seconds until ready, then immediately issued queries.

StepDuration
ready_replicas 0/1 → 1/1~80 seconds (16 polls × 5s)
First query after ready_replicas=1~617ms — NVMe still cold
Rolling warm state (<20ms mean)~11 sequential queries (~2 seconds)
Total: pin → warm serving~90–100 seconds
ready_replicas=N means the compute node is running — not that NVMe is populated. Any deployment runbook that sends traffic immediately after ready_replicas confirmation will hit cold latency spikes on the first 10–15 queries (~600ms each). A warmup pass of ~75 sequential queries is required before serving production traffic.
§4

hint_cache_warm Behavior

turbopuffer exposes a hint_cache_warm API for pre-warming a namespace before a burst. We measured the effect of using it inline (calling the hint, then immediately querying) at p=8 on DBpedia.

ConfigRPSMean latency
Default serverless p=8224 RPS22.9ms
hint_cache_warm inline p=817 RPS459ms
hint_cache_warm used inline is 13× worse than default serverless. The cache-warm RPC is a synchronous call adding ~400ms overhead before each query. It is designed for pre-warming a cold namespace before a burst (send the hint, wait, then serve) — not as a per-query prefix. Using it inline inverts its intended effect entirely.
§5

Internal Search Latency Gap

Measuring internal search latency (the engine’s own processing, excluding network round-trip) reveals an architectural floor difference. At steady state on DBpedia (unfiltered), turbopuffer internal search latency is consistently ~10ms while Qdrant is ~1.9ms.

The ~10ms tpuf vs ~2ms Qdrant server-latency floor is architectural (NVMe vs RAM)
The gap reflects the fundamental storage medium: HNSW traversal on RAM vs. SPFresh centroid reads from NVMe. No configuration on either side can close it.

Cross-Namespace Contention (Serverless)

A high-throughput "aggressor" namespace and a "victim" namespace both sharing the same API key on serverless. The aggressor runs at full blast; we measure what happens to victim latency.

Victim p50 Latency — Baseline vs Under Aggressor Load
Serverless co-locates all API-key namespaces on one host. Pinning provides machine isolation.
Serverless noisy-neighbor: a bursty tenant triples victim latency (14.9ms → 52.8ms, +255%). Pinning reduces this to a 20% variance (16.3ms → 19.5ms). If your workload includes any bursty tenants in serverless mode, all other tenants under the same API key are affected.

Write Throughput: Serverless vs Pinned

Does pinning a namespace affect write performance? We uploaded DBpedia 100K×1536 twice — once serverless, once to a pinned-1r namespace — using identical batch size and client configuration.

ModeWPSbatch_p50batch_p99server_p50server_p99
Serverless624192ms352ms180ms341ms
Pinned-1r633188ms295ms176ms282ms
Pinning has zero effect on write throughput — writes hit the S3 WAL either way
624 vs 633 WPS is within noise. The slight p99 improvement on pinned (295ms vs 352ms) is consistent with lower noisy-neighbor contention on a dedicated machine — not a write-path difference. This confirms that turbopuffer writes go directly to the S3 WAL in both modes; the pinned replica only maintains an NVMe read cache and is not involved in the write path at all. Single-replica tpuf write capacity: ~625 WPS at batch=128 for 1536-dim vectors, independent of deployment mode.
§8

Concurrent Write-Read Dynamics

Both engines were loaded from empty while a reader fired every 500ms, starting at the same moment as the writers — no pre-loading, no index warmup. 100K×1536 DBpedia vectors uploaded in ~254s; queries continued for 120s after the last write. Recall uses the same ground-truth queries as all other benchmarks.

Phase turbopuffer — p50 / p99 / recall Qdrant — p50 / p99 / recall
During upload (0–254s) 30ms / 325ms / 49% 18ms / 46ms / 49%
After upload (254–374s) 21ms / 58ms / 99% 7.9ms / 15ms / 99%
DBpedia loaded from empty · every query plotted over wall-clock time
Both engines start empty; a reader fires every 500ms. Dashed line = upload complete (~254s). Recall climbs to ~99%; tpuf's WAL brute-force scan (toggle "exhaustive") keeps recall healthy at the cost of p99 spikes until SPFresh catches up. Hover a point; click an engine to toggle.
tpuf's WAL brute-force scan keeps recall healthy during upload, at a p99 cost
Every unindexed vector in the WAL is brute-force scanned on each query (exhaustive_search_count averages 18,056 during upload, max 50,560). This scan rescues recall — without it, freshly uploaded vectors would be invisible to SPFresh. The cost: p99 inflates to 325ms vs 58ms post-upload. The exhaustive scan count trails to zero within ~14s of the last write in this incremental scenario (SPFresh builds continuously during upload, so only the final WAL batch remains at end). A cold full build from an empty namespace took 25–268s for 100K×1536d across 5 runs, depending on shared indexer availability (see §3 in the main report).
Both engines sit at ~49% recall at the upload midpoint (half the data loaded)
— consistent with the expected value when half the dataset is loaded (neighbors are uniformly distributed, so ~50% of any query's true neighbors are already present). Qdrant's HNSW optimizer stays within 3% of the write front throughout, and its latency improves 2.3× once upload completes (18ms → 7.9ms p50). tpuf's WAL scan preserves recall at the cost of 5.6× p99 inflation during upload (58ms → 325ms).

Qdrant Disk Mode vs turbopuffer (EBS Cold/Warm)

Qdrant supports mmap-based vector storage (on_disk=True) where vectors and/or the HNSW graph are served from disk on demand. We benchmarked two configurations against turbopuffer using DBpedia 100K×1536 on Qdrant Cloud (AWS us-west-2, 64 GB RAM, EBS storage) with clean state after each upload. disk-vec: vectors on EBS, HNSW graph in RAM. disk-all: both on EBS.

Qdrant disk-mode cold start is a tail disaster (p99 1,457ms) until the page cache warms
p50 cold is fine (7ms — some pages already in OS cache from the upload process), but p99=1,457ms exposes the EBS random I/O storm when page faults cascade across uncached regions. After ~1,000 warmup queries, the entire 586 MB dataset (100K×1536×4B) fits in 64 GB page cache and disk mode becomes statistically indistinguishable from pure-RAM mode (7.1ms vs 6.9ms p50, 10.4ms vs 9.4ms p99). The EBS cold/warm gap is real — but only materializes on first access after upload or node restart.
ef=64 is the warm-disk sweet spot; putting the graph on disk too adds no real overhead
6.4ms p50 (+7% faster than RAM ef=128 — fewer candidates, fewer potential page faults), 97.4% recall (only −1% from RAM). Putting the HNSW graph on disk too (disk-all) adds no measurable overhead — the graph is <10 MB vs 586 MB of vector payload. At p=8 concurrency all warmed configs converge to 17–21ms p50; tpuf (48.7ms p99) edges out most Qdrant disk configs in tail latency at high concurrency, but loses 2× at p=1 steady-state.
